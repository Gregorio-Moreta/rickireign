## What this is
A calm, premium marketing site establishing **Ricki Reign** as a founder, facilitator, and organizational leader; lets people follow her (newsletter + socials) and routes them to work with her. A visitor should leave able to answer: who is Reign, what does she do, how do I work with her. **No payments, no user accounts.** Single-scroll home + `/journal` (blog) + `/privacy` `/terms`.

## Stack & architecture
- **Next.js 16 (App Router) + TypeScript strict + Tailwind v4** (tokens in `app/globals.css` `@theme`, no `tailwind.config.ts`). React 19. Top-level `app/` `components/` `lib/` — **no `src/`**, import alias `@/*`.
- **Dual deploy: Vercel AND Cloudflare Workers** (via OpenNext, `@opennextjs/cloudflare`). Both are live and must stay green.
- **Sanity v6** for content — **standalone Studio** in `studio/` (its own package), project `zsuyhr45`, public `production` dataset. App reads published content with a **token-less CDN client**.
- **GA4** via `@next/third-parties` (consent seam in place, gating is Phase 3). **Brevo** (newsletter, Phase 3), **Calendly** (booking), **Cloudflare Turnstile** (forms, Phase 3).
- Node **24** is pinned (`.node-version`) so local/Vercel/Cloudflare all use npm 11.

## Rules for every session
- **Plan first.** Non-trivial work gets a plan approved before code (the human signs off at the plan and again before merge).
- **Never delete branches.** No `gh pr merge --delete-branch`, no `git branch -D`, no `git push --delete` unless explicitly asked for a named branch. Every branch lives on **both** local and the remote. Numbered branches `NNN-summary` (`000-foundation`, `001-content-model`, `002-…`), Conventional Commits, co-author trailer `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.
- **Secrets server-only.** Only genuinely public values get `NEXT_PUBLIC_*`. Server secrets (Brevo key, Turnstile secret, Sanity tokens) are never `NEXT_PUBLIC_`, never committed (`.env*` gitignored except `.env.example`). On Cloudflare, `NEXT_PUBLIC_*` are **plaintext build vars** (correct — they're public); un-prefixed secrets become encrypted secrets (Phase 3).
- **Sanity reads are token-less** (public dataset via CDN). The app must never carry a write/editor token.
- Subagents exist (`frontend-builder`, `backend-builder`, `code-reviewer`, `git-manager`, `qa-tester`) and run in **isolated worktrees** under `.claude/worktrees/` — their output must be consolidated onto the working branch. ## Key decisions & why
- **Dual deploy (Vercel + Cloudflare).** The human wants both as a safety net; treat both as first-class. (Expanded beyond the original Vercel-only plan, deliberately.)
- **Standalone Studio, not embedded `/studio`.** Embedding compiles the Studio into *both* the Vercel and Cloudflare builds (slow, heavy), needs Studio CORS+CSP, and ties Studio updates to app redeploys. Sanity recommends standalone for new Next.js. The app only `next-sanity`-fetches.
- **Token-less CDN read client + public dataset.** Public marketing content; `secure-defaults`. Server-side reads in Server Components mean the public site needs **no CORS** and **no token** anywhere.
- **CORS scoped to `localhost:3000` + `https://rickireign.vercel.app`, never `*.vercel.app`.** A credentialed wildcard would let any `*.vercel.app` site ride a logged-in editor's session. The Studio (browser-credentialed) is the only thing that needs CORS; the site itself doesn't (SSR).
- **Sanity/Studio points at `rickireign.vercel.app` (dev/staging), not `rickireign.com`.** The real domain still hosts the *old* site we're replacing; cut over later.
- **One dataset; environment differences come from Vercel's built-ins** (`VERCEL_ENV`/`VERCEL_URL`), not per-env datasets — keep it simple.

## Gotchas (don't re-learn these the hard way)
- **EPIPE on Vercel build:** `initOpenNextCloudflareForDev()` only guards on AsyncLocalStorage, so it runs during `next build` and crashes with `unhandledRejection: write EPIPE`. It is guarded in `next.config.ts` with `if (process.env.NODE_ENV === "development")` + dynamic import. Keep that guard.
- **Cloudflare `npm ci` "Missing esbuild from lock":** caused by an npm-version mismatch (CF defaulted to Node 22/npm 10 reading an npm-11 lockfile). Fixed by `.node-version` = 24. Keep local npm and CI aligned.
- **Vercel "No Output Directory named public":** Vercel auto-detected framework "Other". Fixed by `vercel.json` `{"framework":"nextjs"}`.
- **Cloudflare deploy via `wrangler.jsonc` overrides remote Worker config:** it wipes dashboard *runtime* vars and re-enables `workers_dev`/`preview_urls` each deploy. Manage runtime env via `wrangler.jsonc` `vars` / `wrangler secret put`. (Build vars used by `next build` are separate Workers-Builds settings and are NOT wiped.)
- **`NEXT_PUBLIC_*` are inlined at `next build` time** → on Cloudflare they must be **Workers-Builds *build* vars**, NOT the runtime Variables section (which `next build` never reads and `wrangler.jsonc` wipes). Phase 2 deploys failed repeatedly (`/_not-found` threw "Missing NEXT_PUBLIC_SANITY_*") until this was understood. Because the Sanity `projectId`/`dataset` are public constants, `lib/env.ts` now commits them as defaults (`process.env.… || "zsuyhr45"` / `"production"`) so the build can't break on a missing build var; an env var still overrides. Apply the same default-or-build-var rule to future public keys (Turnstile site key, Calendly URL); keep real **secrets** out of `lib/env.ts` and out of `NEXT_PUBLIC_*`.
- **ESLint flat config ignores `.gitignore`.** Generated/foreign dirs must be in `eslint.config.mjs` `globalIgnores`: `.next`, `.open-next`, `.wrangler`, `.vercel`, `studio/**`. Otherwise ESLint walks bundled JS and reports thousands of errors.
- **App `tsconfig.json` excludes `studio`** (its `**/*.ts` include would otherwise typecheck the Studio with the wrong config).
- **`@sanity/image-url` is a required direct dep** — `next-sanity` does NOT bundle it. Import the **named** `createImageUrlBuilder` (default export is deprecated); `SanityImageSource` is on the package's main entry (not `/lib/types/types`).
- **Sanity seeding order:** publish referenced docs (e.g. `business`) **before** creating the doc that references them (`homePage`), or the mutation fails "references non-existent document." Singletons use a fixed `_id` (`siteSettings`, `homePage`) so the Studio Structure maps to them.
- **The guard hook blocks any Bash command containing the literal `.env`** (even in an echo/grep comment). Avoid that substring in commands.
- **Never run `sanity debug --secrets`** — it prints the Sanity CLI **user token** to stdout, straight into the session log. Plain `npx sanity debug` answers "logged in, as whom" without credentials. If it does leak: `npx sanity logout` **revokes server-side** (verified — the old token 401s immediately, it is not just deleted locally), then `npx sanity@latest login --provider github`. Also `chmod 600 ~/.config/sanity/config.json` — the CLI writes it **644**. This project has **no project-level access tokens**, so the manage-console token-deletion flow in Sanity's docs does not apply.
- **Cloudflare Worker size limit is 3 MiB gzip on the FREE plan** (10 MiB paid), measured after gzip by `wrangler deploy`. `opennextjs-cloudflare build` + workerd `preview` do NOT enforce it — only a real deploy does, so a green local build can still fail the CF deploy. Check with `npx wrangler deploy --dry-run --outdir /tmp/x` → "gzip: … KiB". OpenNext already minifies (`minify: !noMinify`, default on). See the `007-cf-sentry-bundle-fix` facts + `docs/SENTRY.md` for the Sentry-driven overage and the dual-SDK fix. (008 measured 2487 KiB — a dep-free content phase; ~585 KiB headroom.)
- **Local `tsc` / `next build` FALSE-FAIL on `cloudflare/worker.ts` — SOLVED (011). The culprit is an untracked `cloudflare-env.d.ts`, not the tsconfig `exclude`.** `npx tsc --noEmit --explainFiles` gives it away: `cloudflare/worker.ts … Imported via "./cloudflare/worker" from file 'cloudflare-env.d.ts'`. `exclude` only filters the **root** file set — a file that something *imports* is in the program regardless, so excluding `cloudflare/worker.ts` can never work while `cloudflare-env.d.ts` imports it. That file is generated by `npm run cf-typegen` (`wrangler types`), is **untracked (not in git), ~530 KB, and unused** — no app code references `CloudflareEnv`. **Fix: delete it** (`rm cloudflare-env.d.ts`); `tsc` is then clean even with `.open-next` absent. This also explains why Cloudflare's own Workers Builds never hit this: a fresh CI clone has no `cloudflare-env.d.ts`. Only run `cf-typegen` if you actually need the types, and delete the output afterwards. (Supersedes the 007 and pre-011 notes claiming the artifact's presence is what matters, and makes the `typescript.ignoreBuildErrors` dance unnecessary.)
- **`wrangler deploy` can leave a Worker serving 404s for its own JS chunks — use `--old-asset-ttl`.** In 011 a local `npm run deploy` reported `6 new uploaded (24 already uploaded)` — all 30 files accounted for — yet **2 of 16 chunks 404'd in production**, including the Turbopack runtime. No runtime chunk = no JS at all: no hydration, dead theme toggle, dead consent modal, dead forms, on an apparently-200 page. Cloudflare **deletes the previous deployment's assets immediately** while new ones are still propagating, so anything wrangler skipped as "already uploaded" can briefly resolve to nothing. Redeploying did NOT fix it (wrangler still thought the files were present) and a version rollback was needed. **Always deploy with `npx wrangler deploy --old-asset-ttl 3600`** (keeps old assets alive through the transition) and **verify assets before declaring success** — fetch `/` cache-busted and check every `/_next/static/...` it references returns 200, retrying a few times, since they converge over ~20–30s. Roll back with `npx wrangler versions deploy <id>@100% --yes`.
- **Rolled-back CF HTML can look broken for ~60s.** `cache-control: s-maxage=60` means the first fetch after a rollback may still be the *previous* version's cached HTML, referencing chunk names that no longer exist. Re-check with `?v=$RANDOM` and look for `x-nextjs-cache: MISS` before concluding a rollback failed.

- **Measuring the CF Worker size REQUIRES `NEXT_PUBLIC_BUILD_TARGET=cloudflare`.** A bare `npx opennextjs-cloudflare build` skips the Sentry tree-shake (that env var is what lets Turbopack DCE `@sentry/nextjs`) and `wrangler deploy --dry-run` then reports **~3360 KiB — "over" the 3 MiB limit. A FALSE ALARM.** Always build via `npm run preview` / `npm run deploy`, or set the var by hand; the correct number is ~2487 KiB. (009 chased this.)
- **Playwright `reuseExistingServer: true` will silently test WHATEVER is on `:3000`.** In 009 an unrelated project's `next dev` held the port, so the whole suite ran against another site and produced 24 bogus failures (`ERR_ABORTED`, missing elements). Check the port first (`curl -s localhost:3000 | grep '<title>'`); if it's busy, run on another port via `E2E_BASE_URL=http://localhost:3100 E2E_WEB_COMMAND="PORT=3100 npm run start"`. Both vars already exist for the CF target.
- **E2E on a contended machine: use `--workers=1`.** Parallel workers against a loaded box produce `page.goto`/`page.evaluate` timeouts that look like real failures but are pure contention — no assertion ever runs. Serially the same specs pass in seconds. Also: the default `webServer.command` is `npm run build && npm run start` with a **180s timeout**, which a cold build blows — pre-build, then point `E2E_WEB_COMMAND` at `npm run start` alone.

## Sentry-in-prod facts (`011-sentry-prod` — don't re-learn)
- **Three of the four reported symptoms were misdiagnoses.** `GET /monitoring` → 404 on Vercel is CORRECT: the tunnel rewrite only matches when the request carries `?o=`, which the SDK always sends. The tunnel was working on BOTH targets all along — `POST /monitoring?o=…&p=…&r=us` returns Sentry's own **401** with its ingest headers (`access-control-expose-headers: x-sentry-error,…`), byte-identical to hitting `o4511575656497152.ingest.us.sentry.io` directly. **Never test the tunnel with a bare `GET`** — assert on the POST.
- **The real client-side fault was Cloudflare-only:** `NEXT_PUBLIC_SENTRY_DSN` is inlined at `next build`, and the CF build runs in Workers Builds where it was never set, so `instrumentation-client.ts` shipped `enabled: Boolean(undefined)` = **false**. CF served the full 284 KB SDK with **zero** occurrences of the org id and no `sentry-trace`/baggage in the HTML, while Vercel had both. The DSN in `wrangler.jsonc` is a **runtime** var and never reaches the build. Fixed by committing the DSN as a default in `lib/env.ts` (`publicEnv.sentryDsn`) — the DSN is public and already committed in `wrangler.jsonc`. Localhost is excluded in `instrumentation-client.ts` so dev/E2E stay silent; **preview deploys DO report** (unlike GA).
- **BIGGER, unreported fault — CF server capture was structurally near-zero.** OpenNext catches every Next-level error and logs it instead of rethrowing (`@opennextjs/aws/dist/core/requestHandler.js`: `catch (e) { error("NextJS request failed.", e); await tryRenderError("500", …) }`), so `@sentry/cloudflare`'s `withSentry` only ever sees a finished 500 **Response** and captures nothing (`request.js` calls `captureException` only from its own `catch`). Fixed with **`Sentry.captureConsoleIntegration({ levels: ["error"] })`** in `cloudflare/worker.ts` — promotes the swallowed `console.error` to a real event at ~zero bundle cost. Do NOT "fix" this by pulling `@sentry/nextjs`'s server SDK back in; that is exactly what the 007 split prevents.
- **Diagnostic that tells the two apart:** a 500 **with** `x-opennext: 1` was swallowed by OpenNext (only `captureConsole` sees it); a 500 **without** that header escaped into `withSentry`. Both were reproduced in prod.
- **`@sentry/cloudflare` attaches POST bodies by default.** `sendDefaultPii: false` suppresses cookies/headers but NOT bodies — `httpServer.js` defaults `maxRequestBodySize` to `"medium"`, so `/api/newsletter` and `/api/contact` submissions (email addresses, free text) were being sent. Now pinned to `"none"`.
- **Worker events had no `release` and no `environment`** — both targets reported as indistinguishable `production`. Now `environment: "cloudflare"` + `release` from the `CF_VERSION_METADATA` binding (added in `wrangler.jsonc`).
- **Source maps: debug IDs were always injected, upload never happened.** `canUploadSourceMaps()` returns false without an auth token and only `logger.warn`s — which our `silent: !process.env.CI` swallows. Vercel DOES upload (33 files, verified in its build log). `org`/`project` now have committed defaults (public identifiers). `SENTRY_AUTH_TOKEN` is a **secret**: it must be a Workers-**Builds** *build* secret — a runtime `wrangler secret put` is the wrong store and does nothing for source maps.
- **Vercel "Sensitive" env vars can't be read back.** `vercel env pull` returns `SENTRY_AUTH_TOKEN`, `BREVO_API_KEY` and `TURNSTILE_SECRET_KEY` **empty** while other vars come back with values. Don't plan on recovering those — mint a new token instead. (Also means `vercel env pull` can't seed a local env file for the live-form tests.)
- **The capture probes are permanent and fail-closed.** `lib/sentry-check.ts` + `app/api/sentry-check/route.ts` + a branch in `cloudflare/worker.ts` (`/api/sentry-check/worker`). With `SENTRY_CHECK_TOKEN` unset they are a bare 404, and `tests/e2e/sentry-check.spec.ts` asserts that. The Next route proves the OpenNext-swallowed path; the Worker branch throws *before* OpenNext to prove `withSentry`'s own path. Set the token, probe, then **remove it from both targets**.
- **The CF `/monitoring` 500 was an `@opennextjs/aws` bug, not Sentry.** Its `routeHasMatcher` `query` branch does `new RegExp(value ?? "").test(query[key] ?? "")` with **no presence check** (its own header/cookie branches have one, and Next's `matchHas` returns false for undefined), and Sentry writes its conditions as `\d*` — so an **absent** `o`/`p` matched, compiled with empty params, threw in `path-to-regexp`, and rendered OpenNext's `/500`. Guarded in `cloudflare/worker.ts`. **Never add `app/monitoring/route.ts`** — a real route makes OpenNext skip the `afterFiles` rewrites and would kill ingest on BOTH targets.
